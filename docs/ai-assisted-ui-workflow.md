# 바로록 AI 보조 UI 디자인·구현 절차

이 문서는 이미지 생성, 디자인 스킬, 코드 구현, 브라우저 검증이 서로 다른 기준으로 움직이지 않게 하는 프로젝트 작업 순서다. 디자인 결과물보다 의사결정의 출처와 검증 가능한 실제 화면을 우선한다.

## 1. 기준의 우선순위

다음 순서에서 앞선 항목이 뒤의 일반 지침보다 우선한다.

1. 사용자가 승인한 화면 방향과 명시한 기능 범위
2. `AGENTS.md`, `docs/design.md`, 화면별 레이아웃 사양
3. 현재 제품의 실제 데이터 계약, 상태 전환, 접근성, 공통 컴포넌트와 토큰
4. 프로젝트의 기존 화면과 테스트
5. 외부 디자인 스킬과 일반 UI 가이드

생성 이미지는 시각 방향과 구도를 합의하는 참고 자료다. 이미지에 우연히 생긴 기능, 문구, 크기, 픽셀 배치를 제품 계약으로 해석하지 않는다.

## 2. 스킬의 역할 분리

| 역할 | 사용 수단 | 담당 범위 | 담당하지 않는 범위 |
|---|---|---|---|
| 작업 조율 | `ui-design-coach` | `new`·`refine`·`review` 분류, 범위 제한, 필요한 디자인/검증 스킬 선택 | 모든 화면의 세부 미감을 직접 결정하는 일 |
| 시각 방향 | `frontend-design` | 주제에 맞는 색·타이포·구도·대표 장면, 획일적인 AI 미감 방지 | 저장값, 비동기 상태, 회귀 테스트, 배포 절차 |
| 실제 화면 완성도 | `impeccable` | layout·polish·harden 등 목적별 제작과 제한된 확인 패스 | 프로젝트 전체 작업 순서와 커밋 판단의 단일 소유 |
| 기술 UI 검사 | `web-design-guidelines` | Vercel의 최신 웹 인터페이스 지침에 따른 키보드·포커스·폼·모션·문구·성능 점검 | 제품의 시각 방향 결정 |
| 위험 검토 | `reviewer` | 변경 위험에 맞는 UX·기능·회귀 검토 범위와 agent 분리 결정 | 디자인 제작 자체 |
| 구현 반복 | `lmo-audio-iterative-dev-loop` | 작은 구현, 좁은 테스트, 검토, P2 분류, 종료 조건 | 새로운 시각 콘셉트 발굴 |
| 비트맵 제작 | `imagegen` | 고래·산호·질감·합성 시안 등 래스터 이미지 | React 구조, SVG/CSS로 충분한 UI, 제품 상태 계약 |

디자인 스킬에도 `계획 → 제작 → 자체 검토` 과정이 일부 포함되어 있지만, 저장 데이터 보존·테스트·agent 검토·중지 조건까지 모두 소유하지는 않는다. 전체 단계는 `ui-design-coach`와 프로젝트 반복 절차가 조율한다.

## 3. 기본 진행 단계

### 0단계 — 목표와 경계

- 이번에 완료할 화면과 사용자의 핵심 행동을 한 문장으로 고정한다.
- 보존할 기능·데이터와 제외할 화면을 적는다.
- 사용자 선택이 필요한 시각 방향만 질문한다.

### 1단계 — 현재 제품 확인

- 작업 트리, 최근 관련 변경, `docs/design.md`, 승인 이미지, UI 구조 자료를 확인한다.
- 대상 컴포넌트, 공통 토큰, 실제 상태와 관련 테스트를 확인한다.
- 다른 세션이나 다른 프로젝트의 서버·오류·아티팩트를 섞지 않는다.

### 2단계 — 시각 방향 탐색

- 방향이 정해지지 않았을 때만 2~3개의 제한된 시안을 만든다.
- 주제, 대표 장면, 색, 표면, 정보 밀도와 한 가지 기억 요소를 비교한다.
- 사용자가 한 방향을 선택하면 미선택 시안은 구현 근거로 사용하지 않는다.

이미 승인된 시안이 있으면 이 단계를 반복하지 않는다.

### 3단계 — 구현 계약

- 레이아웃 폭·높이·반응형 전환·장식 safe zone을 수치화한다.
- 기본·선택·오류·로딩·이어하기·빈 상태를 상태표로 확인한다.
- 기존 컴포넌트를 재사용할 부분과 새로 만들 부분을 정한다.
- 데이터 소유자와 분석 요청 payload처럼 시각 변경이 침범하면 안 되는 계약을 적는다.

문서는 구현 결정을 고정할 만큼만 작성한다. 구현 전에 거대한 디자인 시스템이나 모든 미래 테마 API를 만들지 않는다.

### 4단계 — 가장 작은 완성 단위 구현

- 한 화면의 대표 상태를 실제 코드로 끝까지 연결한다.
- 기존 상태 로직을 보존하고 시각 경계가 분명한 부분부터 변경한다.
- 공통 컴포넌트 추출은 같은 계약이 두 번 이상 반복되거나 독립 테스트 가치가 있을 때 한다.
- 미래 테마는 CSS 변수나 `data-theme` 같은 얇은 확장점만 둔다.

### 5단계 — 실제 화면 검증

- 지원 너비와 낮은 높이에서 실제 화면을 캡처한다.
- 승인 이미지와 위계·비율·밀도·장식 침범을 비교한다.
- 기본 상태뿐 아니라 파일 선택, 오류, 로딩, 이어하기, 긴 문구를 확인한다.
- 키보드, 포커스, 강제 색상, 투명도·모션 감소와 가로 스크롤을 확인한다.
- 같은 Windows·브라우저 환경에서 스크린샷 기준을 만들어 시각 회귀의 잡음을 줄인다.

### 6단계 — 위험별 검토와 한 번의 보정

- 큰 관점: 사용자 흐름, 정보 위계, 상태 소유권, 기능 보존을 검토한다.
- 작은 관점: overflow, disabled/loading, stale state, 접근성, 테스트 누락을 검토한다.
- P0/P1과 현재 화면을 직접 방해하는 P2만 수정한다.
- 한 번에 묶어 수정하고 한 번 더 확인한 뒤, 실제 결함이 없으면 끝없이 다듬지 않는다.

### 7단계 — 사용자 승인과 다음 화면

- 실제 캡처와 검증 결과를 사용자에게 보여준다.
- 승인 전에는 다음 화면으로 테마를 확장하거나 커밋·푸시하지 않는다.
- 첫 화면이 승인되면 반복되는 토큰·표면·장식 규칙을 추출해 다음 화면에 적용한다.

## 4. 바로록 새 회의록에 적용하는 순서

현재 작업은 0~3단계를 완료한 상태다. 다음 구현은 아래 한 묶음으로 진행한다.

1. `Layout`에 `minutes` 전용 전체 창 shell 상태를 추가한다.
2. `MeetingWriter`의 기능·분석 상태는 보존하고 입력 상태에 ocean canvas를 적용한다.
3. 바다 기본층과 햇빛을 CSS로 만들고 고래·산호는 분리된 투명 에셋으로 배치한다.
4. 기존 업로드·회의 정보·분석 시작 DOM에 테마 클래스를 적용한다.
5. 참석자 구분 UI는 제거하되 분석 시작 직전에 설정의 최신값을 payload에 사용한다.
6. 1024·1280·1440·1600px와 workspace 720·800·900px에서 검증한다.
7. UI/UX와 회귀 위험을 분리 검토한 뒤 사용자에게 실제 화면을 제시한다.

첫 구현에서는 대규모 `MeetingWriter` 분해나 범용 테마 엔진을 함께 하지 않는다. 바다 테마가 실제 화면에서 승인된 뒤 반복되는 경계만 추출한다.

## 5. 중지 조건

다음을 모두 만족하면 해당 화면 작업을 멈추고 사용자 승인을 기다린다.

- 선택한 화면의 주 행동이 기존과 동일하게 작동한다.
- 저장값과 분석 요청 계약이 보존된다.
- 지원 너비에서 가로 overflow와 UI·장식 충돌이 없다.
- 키보드와 포커스 경로가 유지된다.
- 오류·로딩·이어하기 상태가 접근 가능하고 레이아웃을 깨지 않는다.
- 좁은 검사, 타입 검사, 브라우저 검증과 현재 범위 agent 검토에 차단 문제가 없다.

## 6. 외부 지침을 받아들이는 원칙

- Vercel 가이드는 구현 후 기술 완성도 검사에 사용하고, 브랜드나 구도를 대신 결정하게 하지 않는다.
- Anthropic 계열 `frontend-design`은 독창적인 방향과 제작 품질에 사용하되, 프로젝트의 기능 계약과 승인 시안을 우선한다.
- OpenAI/Codex의 시각 참조·반복 개선 방식은 승인 이미지와 실제 브라우저 결과 사이의 왕복에 사용한다.
- 외부 가이드가 업데이트돼도 기존 사용자 승인과 제품 계약을 자동으로 뒤집지 않는다.
