# 바로록 시작 화면·공통 UI 기반 계획

상태: 구현 전 검토안

이 문서는 현재 시안과 기존 제품 화면을 하나의 구현 기준으로 정리한다. 이 단계에서는 React/CSS 화면을 만들지 않는다. 화면 수, 상태 우선순위, 공통 셸, 컴포넌트 소유권, 배경 에셋 방식과 검증 순서를 먼저 고정한다.

## 1. 목표와 범위

### 목표

- 첫 진입 화면이 사용자의 데이터 상태에 맞게 달라지되 레이아웃은 흔들리지 않는다.
- 시작 화면, 새 기록, 분석 진행이 같은 작업 캔버스와 배경 규칙을 사용한다.
- 회의 상세와 설정은 기존 문서형 작업면을 유지한다.
- 시안별로 셸, 카드, 상태 판정을 다시 만들지 않는다.
- 현재 없는 로딩·오류·좁은 창 상태도 구현 전에 계약으로 남긴다.

### 이번 계획의 범위

- 시작 화면 3종
- 기존 새 회의록, 분석 진행, 회의 상세 3개 탭, 설정
- 공통 레이아웃과 공통 컴포넌트
- 재개 가능 상태와 최근 회의 상태의 데이터 소유권
- WebP 전체 배경판 사용 방안
- 단계별 구현 및 검증 게이트

### 제외

- 이 문서 단계에서의 React/CSS 구현
- 회의 데이터 형식 변경
- 통계, 클라우드, 협업 등 현재 제품에 없는 기능 추가
- 시안에만 보이는 기능을 실제 기능처럼 노출하는 것

## 2. 화면 수 결론

시각 참고 이미지는 9개가 필요하지만 React 페이지를 9개 만들지는 않는다.

| 구현 작업면 | 주요 시각 상태 | 구현 단위 |
|---|---|---|
| 시작 작업면 `StartWorkspace` | 비어 있음 / 최근 작업 있음 / 재개 가능 | 컴포넌트 1개 + 상태 변형 3개 |
| 새 회의록 입력 | 기본 입력 / 파일 선택 / 재개 준비 / 유효성 오류 | 기존 `MeetingWriter` 입력 작업면 |
| 분석 진행 | 진행 / 정체 / 중지 요청 / 중지 / 실패 | 기존 `MeetingWriter` 진행 작업면 |
| 회의 상세 | 대화록 / 회의 요약 / 회의록 | 기존 `MeetingHistory` 작업면 + 탭 3개 |
| 설정 오버레이 | 일반 / 모델 등 설정 내부 탭 | 현재 작업면 위의 기존 modal overlay 1개 |

따라서 수량은 다음처럼 구분한다.

- 코드 구조: **5개 작업면(surface family)**
- 1차 시각 검토 기준: **9개 대표 화면**
  - 시작 화면 3개
  - 새 회의록 1개
  - 분석 진행 1개
  - 회의 상세 3개
  - 설정 1개
- 로딩, 오류, 생성 중, 좁은 창 등은 새 페이지가 아니라 각 작업면의 상태 검증 항목으로 관리한다.

## 3. 첫 진입 상태 우선순위

`StartWorkspace`의 변형은 저장된 화면 이름이 아니라 현재 데이터에서 계산한다.

| 우선순위 | 조건 | 표시 결과 | 주 행동 |
|---:|---|---|---|
| 0 | 현재 세션에서 분석 중 | 현재 분석 화면 유지 | 분석 계속 보기 |
| 1 | 재개 상태 동기화 전 | 고정 높이 로딩 상태 | 없음 |
| 2 | 실제로 재개 가능한 작업 존재 | 재개 변형 | 재개 준비 화면 열기 |
| 3 | 저장된 회의 없음 | 비어 있음 변형 | 새 회의록 |
| 4 | 저장된 회의 있음 | 최근 작업 변형 | 마지막 회의 열기 / 새 회의록 |
| 5 | 동기화 실패 | 마지막으로 신뢰 가능한 상태 또는 재시도 상태 | 다시 확인 |

핵심 규칙:

- 앱이 데이터를 확인하는 동안 비어 있음 화면을 잠깐 보여 주었다가 최근 작업 화면으로 바꾸지 않는다.
- 재개 가능 여부는 로컬 저장값만으로 결정하지 않는다. 백엔드 상태와 복구 결과를 확인한 공통 모델을 사용한다.
- 재개 행동은 즉시 분석을 재시작한다는 뜻이 아니다. 현재 기능 계약에 맞춰 `같은 음성 파일을 다시 선택하면 이어갈 수 있습니다.`라고 안내하고 재개 준비 상태를 연다.
- 완료되었거나 사용할 수 없는 초안은 시작 화면과 사이드바의 재개 목록에서 모두 제외한다.

## 4. 시작 시안 3종 정리

| 시안 | 유지 | 구현 전에 수정할 점 |
|---|---|---|
| A. 비어 있음 | 강한 새 회의록 행동, 3단계 사용 안내, 넓은 여백 | `새 기록`을 선택된 메뉴처럼 표시하지 않는다. |
| B. 최근 작업 | 마지막 작업으로 빠르게 돌아가는 흐름 | 사이드바와 같은 최근 회의 목록을 본문에 반복하지 않는다. 본문에는 마지막 회의 카드 1개만 둔다. |
| C. 재개 가능 | 중단 작업을 가장 먼저 복구하는 흐름 | 완료 회의 목록을 반복하지 않는다. 즉시 재개 표현을 제거하고 같은 파일 재선택 안내를 넣는다. |

세 시안은 콘텐츠만 달라지고 다음은 동일해야 한다.

- 사이드바 폭과 메뉴 위치
- 작업 캔버스 시작점
- 제목 기준선과 최대 콘텐츠 폭
- 배경의 수면광, 고래 위치 원칙
- 주 버튼 크기와 위치 규칙
- 로딩 중에도 유지되는 최소 높이

## 5. 공통 셸과 레이아웃 계약

### 셸은 두 종류만 허용한다

1. `ocean` 셸
   - 시작 화면, 새 회의록, 분석 진행에 사용한다.
   - 별도 상단 Header를 두지 않는다.
   - 사이드바 바로 옆에서 작업 캔버스가 시작한다.
   - 작업 캔버스 하나만 세로 스크롤을 소유한다.
   - 시작 → 새 회의록 → 분석 진행 전환에서 셸 치수가 변하지 않는다.

2. `document` 셸
   - 회의 상세에 사용한다.
   - 기존 최대 `1360px` 프레임과 문서형 여백을 유지한다.
   - 기존 Header와 상세 콘텐츠 레일을 유지한다.

설정은 별도 `AppView`나 셸을 만들지 않고 현재 작업면 위의 기존 modal overlay로 유지한다. 설정을 열어도 아래 작업면의 셸, 배경판과 스크롤 위치는 그대로 유지한다.

문자열 조건을 여러 컴포넌트에 흩뿌리지 않고 `shellVariant: 'ocean' | 'document'` 하나로 계산한다.

### 치수

| 항목 | 고정 기준 |
|---|---|
| 사이드바 | `272px` |
| 시작·새 회의록 콘텐츠 최대 폭 | `1152px` 이내, 화면별 실제 레일은 별도 제한 |
| 상세 콘텐츠 최대 폭 | `1320px` |
| 문서형 앱 프레임 최대 폭 | `1360px` |
| 2열 → 1열 기준 | viewport가 아닌 작업 캔버스 `832px` |
| 우선 검증 창 | `1536×1024`, `1280×720`, `1024×720` |

1024px 폭에서는 사이드바를 축소하거나 모바일 메뉴로 바꾸지 않는다. 남은 작업 캔버스가 한 열로 전환되고 연속 스크롤을 사용한다.

## 6. 배경 에셋 결정안

### 결론

수면광, 고래, 해저 풍경처럼 유기적인 장면은 억지로 SVG로 다시 만들지 않는다. **작업 영역 전체를 덮는 WebP 배경판(background plate)**을 우선 검토한다.

다만 참고 이미지 전체를 그대로 배경으로 사용하지 않는다. 참고 이미지에는 사이드바, 제목, 버튼, 안내 아이콘이 포함되어 있어 반응형 배치와 접근성을 깨뜨린다. 원본에서 다음 요소를 제거한 작업 영역 전용 원화를 제작한다.

- 제거: 사이드바, 모든 글자, 버튼, 카드, 아이콘, 등고선형 UI 장식
- 유지: 바다색, 수면광, 고래, 기포, 해저의 저대비 질감
- 필수 안전 영역: 작업 캔버스 왼쪽과 중앙에 글자와 카드가 올라갈 깨끗한 저대비 공간

### 권장 구성

| 에셋 | 용도 | 배치 원칙 |
|---|---|---|
| `ocean-workspace-wide.webp` | 넓은 작업 캔버스 | `cover`, 우측 상단 초점, 고래가 UI 안전 영역을 침범하지 않음 |
| `ocean-workspace-compact.webp` | 832px 미만 한 열 또는 낮은 창 | 장식 밀도를 낮추고 고래를 약하게 자르거나 제거 |
| CSS 색상·대비 오버레이 | 텍스트와 패널 가독성 보정 | 배경과 UI 사이의 독립 레이어 |

한 장으로 모든 비율을 억지로 맞추기보다 최대 두 개의 의도된 크롭(art-directed crop)을 사용한다. 비균일 확대는 금지하고 `background-size: cover`와 고정 초점 위치를 사용한다.

### UI와 배경의 경계

- 실제 제목, 버튼, 입력, 상태, 단계 안내는 HTML/CSS 컴포넌트로 남긴다.
- 배경 이미지는 장식이며 접근성 트리와 포인터 입력에서 제외한다.
- 배경 위 텍스트 대비가 부족하면 반투명 패널 또는 CSS 오버레이를 조절한다.
- `forced-colors`와 투명도 감소 환경에서는 배경판을 제거하고 단색 배경을 사용한다.
- 시작 화면과 새 회의록은 같은 배경 계열을 사용하되 콘텐츠 가독성에 필요한 오버레이 강도만 상태별로 바꾼다.
- 회의 상세와 설정에는 이 배경판을 사용하지 않는다.

### `분석 시작` 버튼의 이미지·글래스 계약

참고 시안의 고래꼬리와 수면 질감은 사용할 수 있다. 단, 버튼 전체를 글자까지 포함한 한 장의 이미지로 만들지 않고 다음 세 층으로 나눈다.

```text
실제 HTML button
  ├─ CSS glass surface: 반투명 청록, 밝은 hairline, 내부 하이라이트
  ├─ WebP 장식: 투명 배경 고래꼬리 + 제한된 수면 질감
  └─ 실제 UI: 분석 시작 문구, loading spinner, focus ring
```

- 버튼의 hit area, 접근성 이름, disabled, loading, hover, pressed, focus-visible은 실제 `button`이 소유한다.
- `분석 시작` 문구는 이미지에 굽지 않고 HTML 텍스트로 둔다.
- 고래꼬리는 투명 WebP 장식으로 분리하며 흰색 또는 옅은 청록 단색에 가깝게 유지한다.
- 내부 수면 질감은 낮은 대비의 WebP 또는 CSS 오버레이로 사용하고 텍스트 뒤에 강한 무늬가 오지 않게 한다.
- 글래스 테두리는 CSS의 반투명 표면과 1px hairline을 기본으로 한다. 선택 시안처럼 강한 외곽 발광을 상시 표시하지 않고 hover·focus에서만 제한적으로 밝힌다.
- `backdrop-filter`는 지원되는 환경에서만 약하게 사용한다. 기본 표면은 필터가 없어도 충분한 대비가 나와야 한다.
- 외곽 모양은 기존 버튼 반경을 사용하는 둥근 직사각형으로 유지한다. 고래꼬리 실루엣 자체를 클릭 영역으로 만들지 않는다.
- 버튼 전용 장식 에셋 목표 크기는 `80KB` 이하, 상한은 `140KB`로 둔다.
- `forced-colors`, 투명도 감소, 배경 에셋 로딩 실패에서는 단색 primary 버튼과 기존 아이콘으로 안전하게 대체한다.

참고 시안의 넓고 강한 발광 버튼은 시각 방향으로만 사용한다. 실제 구현은 업무용 화면 밀도에 맞춰 `220–240px` 폭, 2열에서 최대 `72px`, 한 열에서 `60px` 높이 계약을 유지한다.

### 성능 기준

- WebP를 기본으로 사용한다. 필요하면 PNG 원본은 제작 보관용으로만 둔다.
- wide와 compact 합계 목표는 `1.2MB` 이하, 상한은 `1.8MB`로 둔다.
- 실제 최대 표시 크기를 넘는 과도한 2배·4배 원본을 런타임에 싣지 않는다.
- 이미지의 고유 크기를 선언하고 최초 렌더 전에 배경색을 지정해 번쩍임을 줄인다.
- 정적 배경을 기본으로 하고 지속적인 영상·큰 패럴랙스 효과는 사용하지 않는다.

이 결정이 승인되면 기존 `new-record-whale-theme-layout-spec.md`의 분리형 환경 에셋 전제는 이 하이브리드 배경판 계약에 맞춰 수정한다.

## 7. 컴포넌트와 상태 소유권

| 단위 | 책임 | 조치 |
|---|---|---|
| `App` | 현재 작업면과 화면 전환 | 문자열 탭을 명시적 `AppView` 타입으로 정리하고 첫 진입을 `start`로 추가 |
| `Layout` / `AppShell` | `ocean`·`document` 셸 선택 | 셸 치수, Header 노출, 스크롤 소유권을 한곳에서 결정 |
| `Sidebar` | 새 기록, 폴더, 회의 목록, 재개 목록, 설정 | 데이터 판정을 자체 복제하지 않고 공통 선택자 사용 |
| `AppBrand` | 로고·제품명 | Header와 Sidebar에 중복된 브랜드 마크를 공통화 |
| `WorkspaceSurface` | 작업 캔버스, 레일, 로딩 최소 높이 | 시작·새 기록·분석의 공통 기하 구조 제공 |
| `OceanBackdrop` | WebP 배경판, 오버레이, 대체색 | 장식만 소유하고 UI 콘텐츠는 소유하지 않음 |
| `StartWorkspace` | 시작 화면 3개 변형 | 3개 페이지가 아니라 `variant` 기반 1개 컴포넌트 |
| `startWorkspaceModel` | 변형 선택과 CTA 대상 계산 | 순수 함수로 분리하고 단위 검증 가능하게 구성 |
| `analysisRecoveryCoordinator` | 앱 부팅 시 백엔드 상태 동기화, 복구 결과 반영, cleanup | `App` 수명 동안 한 번만 마운트하고 공통 snapshot 발행 |
| `analysisResumeState` | snapshot 저장소, 재개 가능 여부, 대표 초안 선택 | `MeetingWriter`·`Sidebar`·시작 화면의 중복 판정 제거 |
| `analysisJobRuntime` | 현재 `MeetingWriter`가 소유한 job claim과 job별 mutation queue | 조정자와 live 분석의 동일 job 경쟁 방지 |
| `StatusChip` | 진행·중지·실패·완료 상태 표현 | 색상과 문구 매핑을 한곳에서 관리 |
| 기존 `Button`, `IconButton`, `ProgressBar`, `AppToast` | 공통 상호작용 | 새 전용 버튼을 만들기 전에 기존 변형으로 수용 |

공통화하지 않는 것:

- 사이드바 회의 행과 시작 화면의 마지막 회의 카드는 행동과 키보드 계약이 다르므로 동일 DOM 컴포넌트로 억지 통합하지 않는다. 날짜·상태 포맷과 뷰 모델만 공유한다.
- 모든 표면을 받는 범용 `Card` 엔진이나 화면 테마 엔진은 만들지 않는다.
- 시작 시안 A/B/C를 각각 독립 페이지로 만들지 않는다.

## 8. 현재 없는 상태도 함께 설계할 항목

### 시작 화면

- 데이터·재개 상태 확인 중
- 회의 없음
- 최근 회의 있음
- 재개 가능
- 동기화 실패와 재시도

### 새 회의록

- 파일 미선택
- 파일 선택 완료
- 필수 입력 오류
- 재개를 위해 같은 파일을 다시 기다리는 상태
- 준비 모델 또는 설정 오류

### 분석 진행

- 정상 진행
- 진행 정체
- 중지 확인
- 중지 요청 처리 중
- 중지됨 / 실패 / 부분 결과 있음

### 회의 상세

- 대화록 없음
- 요약·회의록 생성 전
- 생성 중
- 생성 실패와 재시도
- 원본 음성 파일을 사용할 수 없음

### 설정

- 일반 설정
- 모델 관리
- 저장 중 / 재시작 필요 / 저장 실패

이 항목은 대표 화면 수를 늘리는 페이지가 아니라 상태표와 자동 검증 시나리오로 관리한다.

## 9. 구현 순서

### 0단계 — 계약 승인

- 이 문서의 5개 작업면, 9개 대표 화면, 상태 우선순위를 승인한다.
- WebP 작업 영역 배경판 사용과 wide/compact 최대 2종 원칙을 승인한다.
- 시작 시안 B/C의 중복 목록 제거와 재개 문구 수정을 승인한다.

### 1단계 — 상태 모델부터 분리

- `AppView`, 시작 변형 계산, 화면 전환 이벤트를 타입으로 정의한다.
- 재개 상태 동기화·복구 결과 반영·cleanup을 `App` 수명의 공통 조정자로 분리한다.
- 앱 재시작 뒤 백엔드가 `active`라고 응답한 작업은 곧바로 재개 가능으로 표시하지 않는다. 상태 확인을 계속하고, 완료 결과가 생기면 회의로 가져오며, stopped/failed와 복구 가능 조건이 확인된 뒤에만 재개 CTA를 제공한다.
- 시작의 복구 변형은 `active/checking`과 `resumable` 표현을 같은 레이아웃 안에서 문구와 행동만 바꾼다.
- 공통 snapshot은 `syncStatus: 'idle' | 'syncing' | 'ready' | 'error'`, `lastSuccessfulSyncAt`, `drafts`, `error`를 노출한다. `syncStatus !== 'ready'`이면 마지막 snapshot은 표시할 수 있지만 새 재개 행동은 비활성화하고 `다시 확인`만 제공한다.
- `MeetingWriter`는 새 분석 또는 재개를 시작할 때 job을 claim하고 live 진행·중지·취소 경쟁을 소유한다. 공통 조정자는 claim된 job의 결과 가져오기·회의 삭제·상태 변경을 건너뛴다.
- 공통 조정자와 `MeetingWriter`는 같은 job별 mutation queue를 사용한다. cleanup, 결과 가져오기, 회의 저장과 삭제는 동일 job에서 동시에 실행되지 않는다.
- `MeetingWriter`와 `Sidebar`가 같은 재개 가능 판정을 쓰게 한다.
- 화면을 꾸미기 전에 순수 상태 계산을 좁게 검증한다.

### 2단계 — 공통 셸 고정

- `ocean`·`document` 셸을 명시적으로 분리한다.
- `WorkspaceSurface`, `AppBrand`, `OceanBackdrop`을 구성한다.
- 3개 기준 창에서 사이드바, 스크롤, 콘텐츠 레일이 움직이지 않는지 확인한다.

### 3단계 — 시작 화면 최소 단위

- 로딩 게이트와 비어 있음 변형을 먼저 연결한다.
- 새 회의록 CTA가 기존 입력 화면으로 이동하는지만 검증한다.
- 배경판은 임시 색상 레이어로도 구조 검증이 가능하도록 UI와 분리한다.

### 4단계 — 최근 작업 변형

- 마지막 회의 카드 1개와 새 회의록 행동을 연결한다.
- 사이드바 목록과 본문이 중복되지 않는지 확인한다.

### 5단계 — 재개 변형

- 백엔드와 동기화된 재개 가능 상태만 노출한다.
- 같은 파일 재선택 안내와 기존 `MeetingWriter` 재개 흐름을 연결한다.
- 완료·사용 불가 초안이 다시 나타나지 않는지 검증한다.

### 6단계 — 배경 원화와 마감

- UI가 제거된 wide/compact 배경판을 제작해 WebP로 최적화한다.
- 버튼용 투명 고래꼬리 WebP와 낮은 대비 수면 질감을 별도 제작한다.
- 버튼 문구·테두리·포커스·상태는 이미지에 포함하지 않는다.
- 고래 초점, 패널 안전 영역, 대비, 파일 크기를 검증한다.
- 불필요한 SVG 환경 장식을 걷어내되 실제 UI 아이콘은 기존 아이콘 체계를 유지한다.

### 7단계 — 회귀 검증

- 기존 새 회의록, 분석 진행, 상세 3개 탭, 설정이 유지되는지 확인한다.
- 시작 → 새 회의록 → 분석 진행에서 셸이 점프하지 않는지 확인한다.
- 좁은 창, 낮은 창, 키보드, 포커스, reduced motion, forced colors를 확인한다.

## 10. 검증 게이트

구현 단계에서 다음 좁은 검증을 우선한다.

- `corepack pnpm --dir desktop-app typecheck`
- 변경 파일 중심의 `corepack pnpm --dir desktop-app lint`
- 시작 변형 선택자와 재개 선택자 단위 검증
- 시작 화면 전환 전용 Playwright 시뮬레이션
- 기존 `test:resume-draft-flow`, `test:analysis-stop-flow`, `test:meeting-detail-flow` 중 변경 영향이 있는 흐름
- `1536×1024`, `1280×720`, `1024×720` 캡처 비교

각 크기에서 확인할 공통 항목:

- 가로 스크롤 없음
- Sidebar와 작업 캔버스 경계 고정
- 시작 변형 전환 시 제목·CTA 기준선 이동 없음
- 배경 고래가 글자·카드·포커스 표시를 침범하지 않음
- 배경 로딩 실패에도 모든 기능 사용 가능
- 탭 전환과 상태 알림이 공통 헤더·탭·버튼을 밀지 않음

## 11. 완료·중지 조건

### 완료

- 5개 작업면과 9개 대표 화면의 책임이 코드 구조에 반영된다.
- 시작 3개 변형이 같은 셸과 같은 상태 모델을 사용한다.
- 재개 판정이 `MeetingWriter`, `Sidebar`, 시작 화면에서 일치한다.
- WebP 배경판이 UI와 분리되고 wide/compact에서 안전하게 잘린다.
- 기존 회의 작성·분석·상세·설정 흐름의 좁은 회귀 검증을 통과한다.

### 즉시 중지하고 재검토할 조건

- 시작 화면 때문에 기존 분석 재개 데이터 계약을 바꿔야 하는 경우
- 한 배경판으로 안전 영역을 확보할 수 없어 UI 가독성이 상태마다 달라지는 경우
- 공통 셸 추출이 회의 상세나 설정의 스크롤 계약을 깨뜨리는 경우
- 구현 중 새 기능 또는 데이터 마이그레이션이 필요해지는 경우
