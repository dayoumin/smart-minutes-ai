# LMO 회의 인사이트 Design System

AI 보조 디자인에서 시안·스킬·구현·검증을 적용하는 순서는 `docs/ai-assisted-ui-workflow.md`를 따른다.

## 바로록 제품 전환

- 사용자 표시명은 `바로록`, 설명은 `개인용 로컬 회의록`을 기본으로 한다. 내부 패키지명과 개발 경로는 전환 완료 전까지 유지한다.
- 2026-07-29 사용자가 선택한 네 개의 밝은 데스크톱 시안을 새 기록, 분석 진행, 회의 상세, 설정의 기본 시각 참고로 사용한다.
- 왼쪽 사이드바는 `새 기록`, 폴더, 회의록 목록, 분석 중·이어하기, 설정을 소유한다. 오른쪽 작업면은 새 기록, 분석 진행, 선택한 회의록 상세 중 하나만 표시하며 회의록 목록을 중복 표시하지 않는다.
- 사이드바에는 목적을 반복하는 `회의 기록` 제목, 모든 목록을 다시 뜻하는 `전체 기록`, 시스템 분류처럼 보이는 `미분류` 항목을 두지 않는다. 기본 상태에서는 회의록을 바로 보여주고, 사용자가 실제로 만든 폴더만 탐색 항목으로 표시한다.
- 사이드바의 `새 기록`은 현재 위치를 나타내는 선택 항목이 아니라 생성 동작이므로 테두리·그림자·파란 글자 강조를 두지 않는다. 기본 전경색을 사용하고 hover에서만 옅은 배경을 표시한다.
- 사이드바 회의록은 제목 오른쪽에 `오늘`, `2일`, `1주`, `2개월`처럼 빠르게 훑을 수 있는 경과 시간을 표시한다. 원래 일시는 상세 화면과 보조 설명으로 보존한다. 행의 hover·키보드 focus에서는 경과 시간을 숨기고 같은 자리에 관리 메뉴를 표시한다.
- 회의록·폴더 관리용 세로점 메뉴는 평소 시각적 소음을 만들지 않도록 숨기고, 해당 행의 hover·키보드 focus 또는 메뉴가 열린 동안에만 표시한다.
- `폴더 만들기`는 생성 동작만 제공하고 관리 메뉴를 두지 않는다. 실제 폴더 행의 메뉴는 `상단 고정`, `위로 이동`, `아래로 이동`, `이름 변경`, `삭제`를 제공하며, 회의록 행의 메뉴도 `상단 고정`을 제공한다. 고정된 폴더와 회의록은 각 목록 안에서 먼저 표시하고, 폴더 수동 이동은 고정 폴더끼리 또는 일반 폴더끼리 적용한다. 마우스 사용자는 폴더 이름 행을 끌어 같은 그룹 안에서 순서를 바꿀 수 있고, 키보드 사용자는 메뉴의 위·아래 이동을 사용한다.
- 폴더와 회의록 탐색 목록은 사이드바의 하나의 세로 스크롤 영역을 공유한다. `새 기록`과 하단 설정은 고정해 두고, 폴더가 많거나 창 높이가 낮아져도 마지막 폴더와 관리 메뉴에 접근할 수 있어야 한다. 폴더를 선택하면 해당 회의록 결과가 보이는 위치로 이동하고, 폴더 메뉴는 행에 맞춘 떠 있는 표면으로 화면 안에 배치해 스크롤 경계에서 잘리지 않게 한다.
- 흰 작업면, 옅은 청회색 페이지, 코발트 주 강조색을 기본으로 하고 해양·수산 정체성은 청록 보조색, 파형, 수면·해도 패턴처럼 제한된 브랜드 신호로 표현한다.
- 앱 프레임 내부의 탐색 영역과 작업 캔버스는 같은 `--barorok-mist` 배경을 사용하고, 헤더와 실제 입력·읽기 작업면만 흰 표면으로 올린다. 화면별로 별도 회색 배경을 만들지 않는다.
- 해양 사진이나 생성 이미지를 대화록·기록 정리·보고서 본문 뒤에 배치하지 않는다. 브랜드 이미지는 로그인, 빈 상태, 새 기록 상단처럼 읽기 작업을 방해하지 않는 영역에만 사용한다.
- 시안에만 있는 기능은 구현 요구가 아니다. 실제 데이터와 동작이 없는 메뉴, 상태, 진행 단계, 통계, 내보내기 형식을 화면에 먼저 노출하지 않는다.
- 데스크톱과 웹은 같은 React UI와 디자인 토큰을 공유한다. 실행 환경 차이는 엔진·저장·연결 계층에서 처리하고 화면을 장기 복제하지 않는다.

## 2026-07-30 프로덕션 시각 기준

- `docs/design-assets/barorok-production/`의 화면 시안을 바로록 전면 디자인의 시각 기준으로 사용한다.
- 화면별 기준은 `01-new-record.png`(새 기록), `02-analysis-progress.png`(분석 진행), `03-meeting-transcript.png`(대화록), `04-meeting-summary.png`(기록 정리), `05-meeting-report.png`(보고서), `06-settings-general.png`(일반 설정)이다.
- 시안의 앱 프레임, 거시적 위계, 콘텐츠 밀도, 여백, 표면, 색과 상태 표현은 최대한 가깝게 구현한다. 실제 문구·동작·데이터 계약·접근성은 현재 코드와 이 문서의 규칙을 우선한다.
- 생성 시안에만 나타난 기능이나 값은 자동으로 구현 범위에 넣지 않는다. 특히 진행 단계, 저장 형식, 상태 문구와 버튼은 실제 지원 상태를 확인한 뒤 대응한다.
- 해양 배경은 첫 시안과 보고서 시안처럼 낮은 대비의 추상 수면·해도 선으로 제한한다. `04-meeting-summary.png`의 강한 파도 표현은 배경 강도 기준으로 사용하지 않는다.
- 완료된 회의 상세에서는 분석 중 항목을 표시하지 않는다. `03-meeting-transcript.png`는 이 상태를 수정한 최종 기준본이다.

## 원칙

- 첫 화면은 회의록 작성과 최근 기록 확인에 집중한다.
- 사용자 화면에는 모델명, 파이프라인, 서버 같은 내부 용어를 최소화한다.
- 반복 UI는 `index.css`의 공통 클래스를 우선 사용한다.
- 첫 화면의 제목 위에는 화면 목적을 반복하는 보조 eyebrow를 붙이지 않는다. 화면 목적이 이미 명확하면 제목만 둔다.
- 섹션 제목 앞에는 의미 없는 숫자 원형, 장식 점, 단계 마커를 넣지 않는다. 실제 순서 진행이나 상태를 전달할 때만 단계 표시를 사용한다.
- 기본값 저장, 자동 적용처럼 현재 조작에서 이미 암시되는 내용은 고정 보조 텍스트로 반복하지 않는다. 필요하면 도움말 title/tooltip에만 둔다.
- 카드 반경은 작게 유지하고, 정보 밀도는 업무 도구에 맞게 차분하게 유지한다.
- 넓은 데스크톱 화면에서는 작업면을 적극적으로 사용한다. 중앙에 작은 카드만 띄워 넓은 여백을 남기는 구성을 피한다.
- 상단 메타 정보, 탭, command bar, 본문은 같은 작업 흐름 안에 있는 표면처럼 보여야 한다.
- 탭별 주요 실행 버튼은 관련 선택값과 함께 command bar에 두고, 위치와 높이를 일관되게 유지한다.
- 회의 상세 상단의 일시·목적·원본 파일은 하나의 메타 스트립으로 묶고, 각각을 동일한 강조 카드로 반복하지 않는다. 처리 상태는 작은 상태 칩으로 낮추고 재생 제어와 같은 행에서 스캔되게 한다.
- command bar에서는 현재 탭의 핵심 동작 하나만 primary로 강조하고, 복사·파일 저장·이름 변경 같은 보조 동작은 outline 또는 ghost 계층으로 구분한다.
- 회의 선택, 탭 전환, 생성 진행 중에는 skeleton 또는 고정 높이 상태 UI로 레이아웃 흔들림을 줄인다.
- skeleton은 최초 진입이나 캐시에 없는 회의로 이동할 때만 작업면을 대체한다. 같은 회의의 background refresh는 현재 내용, 포커스, 편집 초안을 유지하고 실패 시 마지막 정상 상태를 보존한다.

## 콘텐츠 레일 규칙

- 데스크톱에서는 앱 전체를 최대 1360px 프레임 안에 중앙 정렬한다. 화면 폭에 따라 좌우 16~48px, 상하 16~32px의 유동 여백을 두고 얇은 경계와 낮은 그림자로 독립된 작업창처럼 보이게 한다.
- 1024px 이하에서는 프레임 바깥 여백과 라운드를 제거하고 화면을 채운다. 데스크톱 폭에서는 높이가 낮아도 프레임을 유지한다.
- 왼쪽 사이드바는 데스크톱에서 약 256~288px 고정 폭을 사용하고, 나머지 오른쪽 영역 안에서 작성·상세 콘텐츠 레일을 적용한다.
- 앱 셸은 사이드바와 가변 메인 영역을 유지하되, 본문은 작업 종류별 최대 폭을 사용한다.
- 회의록 작성 화면은 최대 1152px, 회의 상세 화면은 최대 1320px를 기본으로 한다. 데이터 표와 테스트 결과처럼 폭 자체가 정보량인 화면만 전체 작업 폭을 사용한다.
- 반응형 열 전환은 가능하면 전체 창 너비가 아니라 사이드바를 제외한 실제 콘텐츠 폭을 기준으로 한다.
- 작성 화면의 실제 폭이 832px 미만이면 일시와 회의 목적 같은 병렬 필드를 한 열로 쌓는다.
- 새 기록 제목은 `새 회의록`처럼 짧게 쓰고 20px 수준의 작업 화면 제목으로 유지한다. 영상·음성 파일 등록 영역의 해양 그라데이션은 브랜드 신호로 보존하고, 아이콘·핵심 안내·선택 버튼·지원 형식 배지를 중앙 세로축에 배치한다. 일반 데스크톱에서는 약 192~224px, 낮은 창에서는 약 168px 안팎으로 제한해 회의 정보와 분석 시작 버튼도 첫 화면 안에 유지한다.
- 작성 화면의 실제 폭이 충분하면 왼쪽은 영상·음성 파일 선택과 보조 도구, 오른쪽은 회의 정보로 나눈다. 실행 영역은 두 열 아래에서 카드 전체 폭을 묶고 오른쪽에 정렬하며, 준비 상태를 반복 설명하지 않고 `참석자 구분` 옵션과 `분석 시작`만 둔다. 좁은 작업면에서는 파일 선택 다음에 회의 정보와 실행 동작이 이어지는 한 열로 돌아간다.

### 시작·새 회의록 고래·햇빛 테마 파일럿 예외

- 사용자가 선택한 `docs/design-assets/barorok-concepts/new-record-whale-tail-selected-no-footer.png`, 첫 진입 시안 3종과 `new-record-whale-theme-layout-spec.md`는 시작·새 회의록 화면에 한해 이 문서의 일반 앱 프레임·작성 카드·하단 실행 영역 규칙보다 우선한다.
- 이 예외의 전체 창 shell geometry는 시작·새 기록·분석 진행 작업 영역에 적용해 전환할 때 앱 프레임 크기가 튀지 않게 한다. 새 기록 2열 레이아웃은 `MeetingWriter`의 입력·이어하기 상태에서만 표시하고, 분석 진행 내용의 내부 구조는 기존 기준을 유지한다. 회의 상세에는 이 예외를 적용하지 않으며 설정은 현재 작업면 위의 기존 modal overlay로 유지한다.
- 새 회의록에서는 해양 작업 캔버스를 창 너비까지 사용하는 minutes-scoped shell variant를 허용한다. 사이드바의 실제 폭과 탐색 기능은 기존 컴포넌트 계약을 유지한다.
- 이 variant에서는 기존 workspace padding을 제거하고 해양 캔버스 하나만 세로 스크롤을 소유한다.
- 별도 흰 하단 실행 영역과 구분선을 두지 않고, `분석 시작`을 회의 정보 패널 아래 해양 캔버스 위에 직접 배치한다.
- `참석자 구분` 설정은 설정 화면을 단일 소유자로 사용한다. 새 회의록 화면에서 토글을 제거하더라도 저장값과 분석 요청 payload 계약은 유지하고, 분석 시작 직전 최신 설정값을 사용한다.
- 이 파일럿의 반응형 기준은 viewport가 아니라 사이드바를 제외한 해양 작업 캔버스의 실제 inline size다. 캔버스가 832px 미만이면 한 열로 전환한다.
- 해양 작업면 배경은 사이드바·글자·버튼·카드가 제거된 작업 영역 전용 WebP 배경판을 사용할 수 있다. 넓은 작업면과 좁은 작업면을 위한 최대 두 개의 의도된 크롭을 사용하고, 실제 UI는 HTML/CSS로 유지한다.
- WebP 배경판은 `ocean` 셸의 단일 장식 레이어가 소유한다. `MeetingWriter`나 시작 상태별 컴포넌트가 배경을 각각 만들지 않는다. 배경판 위의 CSS 대비 오버레이는 화면 상태에 따라 강도를 조절할 수 있지만 셸 치수와 스크롤 소유권은 바꾸지 않는다.
- 분석 진행에서도 같은 배경판을 유지하되 CSS 대비 오버레이를 강화해 장면을 낮은 대비로 만든다. 배경 이미지의 마운트 여부가 시작·입력·분석 전환마다 바뀌지 않게 한다.
- 설정은 현재 작업면 위의 modal overlay이므로 열고 닫을 때 아래 `ocean`·`document` 셸과 스크롤 위치를 바꾸지 않는다.
- 참고 시안 전체를 그대로 런타임 배경으로 확대하지 않는다. 고래꼬리처럼 버튼 안에서 필요한 장식은 투명 WebP로 분리하되, 버튼 외곽·문구·포커스·disabled·loading 상태는 실제 HTML/CSS가 소유한다.
- 배경판이나 `backdrop-filter`를 사용할 수 없는 환경에서도 단색 해양 배경, 불투명 패널과 1px 경계로 모든 기능과 대비가 유지되어야 한다.

## 스타일 후보: Compact Monochrome

- 참고 스타일: Refero `brutalist Swiss grid in graphite and chalk` 계열. 흰 작업면, 흑연색 텍스트, 1px hairline border, 낮은 그림자 의존, 조밀한 업무용 정보 밀도를 핵심으로 본다.
- 현재 LMO 브랜드 색상은 유지하되, 첫 화면 작성 패널처럼 반복 작업 표면에는 색상 강조를 줄이고 테두리/타이포/간격으로 구조를 만든다.
- 적용은 전체 앱 전환이 아니라 화면 단위 파일럿으로 시작한다. 우선 `MeetingWriter`의 입력, 업로드 영역, 보조 버튼, 시작 버튼에만 적용하고 결과 상세/상태/참석자 색상은 기존 semantic token을 유지한다.
- 한국어 본문 가독성을 우선한다. Geist 계열은 의존성이 있어도 한국어 UI 전체 폰트로 강제하지 않고, 필요하면 라틴/숫자 중심 보조 스택으로만 검토한다.
- 이 스타일을 확장할 때는 원시 `bg-blue-*`, `text-blue-*`를 새로 추가하지 않고 `index.css`의 `--refero-*` 후보 토큰이나 기존 semantic token으로 매핑한다.

## 핵심 용어

- `회의 요약`: 분석 후 핵심 내용, 주요 주제, 할 일을 보여주는 영역
- `대화록`: 참석자, 시간, 문장을 함께 보여주는 영역
- `음성 파일`: 음성 파일과 영상 파일을 모두 포함하는 업로드 표현. 영상도 분석 대상이지만 사용자는 최종적으로 음성을 분석한다고 이해한다.
- `참석자 구분`: 누가 말했는지 자동으로 나누는 분석 옵션

## 공통 클래스

- `app-panel`: 주요 작업 패널
- `app-panel-header`: 패널 상단 정보 영역
- `btn-ghost`, `icon-button`: 배경 없는 보조 동작과 아이콘 전용 버튼
- `input-field`, `select-field`: 텍스트 입력과 선택 컨트롤
- `settings-dialog`, `floating-panel`, `menu-panel`: 모달, 팝오버, 메뉴 표면
- `tab-list`, `tab-button`, `tab-button-active`: 탭 UI
- `summary-block`: 요약 본문
- `topic-chip`: 주요 주제 태그
- `speaker-turn`, `speaker-meta`: 대화록 행
- `detail-inline-note`, `detail-help-button`, `detail-control-card`: 상세 화면 보조문, 도움말, 입력 제어 묶음
- `speaker-label-panel`, `speaker-summary-*`: 참석자 이름 변경과 참석자별 정리
- `status-note`: 짧은 안내 및 주의 문구
- `resume-draft-card`, `resume-drafts-panel`, `sidebar-resume-draft-button`: 이어하기/미완료 분석 기록

## 버튼 문구 규칙

- 버튼은 동작만 짧게 쓴다. 가능하면 `정리`, `저장`, `취소`, `연결`, `복원`, `선택`, `숨기기`처럼 2~4음절 중심으로 유지한다.
- 버튼에 설명을 넣지 않는다. 이유나 결과는 버튼 아래 보조문이나 상태 배너로 분리한다.
- 같은 동작을 여러 화면에서 반복할 때는 같은 문구를 유지한다.
- 사용자가 내부 구현을 알 필요가 없는 버튼에는 `AI`, 모델명, 서버 용어를 넣지 않는다.

## 상태 표시 규칙

- 완료 상태는 짧은 텍스트보다 아이콘으로 먼저 보여준다.
- 진행 중 상태는 스피너와 짧은 현재형 문구로 표시한다. 예: `정리 중`, `저장 중`, `확인 중`
- 주의나 재실행 필요 상태는 한 단어 또는 짧은 구로 표시한다. 예: `원본 필요`, `대화록 필요`, `수정 필요`
- 복사, 저장, 완료처럼 사용자가 즉시 조치할 필요가 없는 일시 알림은 토스트나 고정 오버레이로 보여주고, 인라인 배너로 본문 레이아웃을 밀지 않는다.
- 인라인 배너는 오류, 경고, 복구 안내, 필수 설정처럼 사용자가 읽고 다음 행동을 결정해야 하는 지속 상태에만 사용한다.
- 성공/실패 후 안내 문구는 한 문장으로 끝낸다. 두 문장 이상 설명이 필요하면 배너가 아니라 별도 도움말로 분리한다.
- 모델 받기 진행 상태는 진행률, 남은 시간, `중지` 버튼만 간결하게 보여준다. 완료 배너나 긴 내부 상태 문구로 레이아웃을 밀지 않고, 실제 준비 확인이 끝나면 체크 아이콘으로 표시한다.

## 포커스와 표면 규칙

- 키보드 포커스는 브라우저 기본 외곽선 대신 `--focus-ring-color`와 `--focus-ring-soft`를 사용한다.
- 버튼과 탭은 2px 외곽선, 입력과 선택 컨트롤은 테두리와 부드러운 링 조합을 사용한다.
- 카드와 일반 컨트롤은 낮은 그림자를 유지하고, 모달·팝오버·메뉴에만 `--shadow-overlay`를 사용한다.
- 반복 작업 표면은 `--radius-card`, 버튼과 입력은 `--radius-btn`, 모달은 `--radius-dialog`를 사용한다. 화면 파일에서 10px, 12px처럼 임의 반경을 새로 만들지 않는다.

## 회의 요약 / 대화록 화면 규칙

- 섹션 제목은 결과 이름만 쓴다. 예: `정리`, `대화록`, `주제별 정리`
- 결과 카드 안에는 결과, 상태, 동작을 분리해서 배치한다. 설명 문구를 카드마다 반복하지 않는다.
- 주제별 정리, 참석자별 정리, 참석자 이름 변경처럼 반복 사용되는 기능은 짧은 보조문 한 줄만 둔다.
- 빈 상태 문구는 무엇이 없는지와 다음 행동만 남긴다. 예: `주제별 정리 내용이 없습니다. 대화록을 확인해 주세요.`
- `대화록`, `기록 정리`, `보고서`는 3개의 산출물 탭으로 유지한다. 각 탭의 액션은 탭 본문 상단 command bar에 모은다.
- 대화록 발화 행은 speaker, 시간, 상태 배지, 발언 내용을 분리해 긴 회의에서도 빠르게 스캔되게 한다.
- 긴 대화록은 발화마다 카드와 본문 버블을 중첩하지 않는다. 화자 색은 작은 식별 신호로 제한하고, hairline 구분선과 일관된 행 간격으로 하나의 읽기 리스트를 만든다.
- 기록 정리의 `정리 기준`, 보고서의 `보고 양식`은 각 탭의 생성/저장 버튼과 같은 줄에서 다룬다.
- 보고서 양식은 보고서 생성 단계에만 적용하고, 기본 기록 정리 프롬프트와 섞지 않는다.

## 설정 화면 기준

- 설정 항목이 적을 때는 별도 설정 사이드바를 만들지 않고 상단 탭을 유지한다. 카테고리가 늘어나 탐색 비용이 생길 때만 좌측 내비게이션으로 전환한다.
- 일반 설정은 `파일`, `분석`, `보관`, `문제 해결`처럼 사용 목적에 따라 한 열로 묶는다.
- 토글 설정은 제목과 설명을 왼쪽에, 스위치를 오른쪽에 정렬한다. 모든 항목을 독립된 회색 카드로 만들거나 2열 카드 그리드로 나열하지 않는다.
- 설정 저장은 즉시 반영을 기본으로 하고, `저장 중`과 `저장됨` 상태가 주변 레이아웃을 움직이지 않도록 고정 공간을 둔다.
- 모델 상태 화면은 준비 상태와 필요한 파일을 `models` 폴더에 넣는 짧은 안내만 보여준다.
- 분석 탭은 기본값을 유지하되, 필요할 때 조정하는 옵션만 둔다.
- 기능 없는 정보 탭은 두지 않는다. 사용자가 조정하거나 확인할 수 있는 설정만 남긴다.
- 모델 탭은 사용자가 직접 누른 상태 확인만 `확인 중`으로 보여준다. 자동 반복 확인, `최근 확인` 시간, 중복 완료 안내는 일반 사용자 화면에 고정 표시하지 않는다.

## 피해야 할 표현

- 사용자 화면에서 특정 모델명으로 기능을 설명하지 않는다.
- 첫 화면 제목 위에 중복 분류 라벨을 고정 노출하지 않는다.
- 섹션 제목 앞에 정보 없는 번호 원형이나 장식 기호를 붙이지 않는다.
- `기본값 저장`처럼 현재 컨트롤의 보조 설명을 별도 텍스트로 반복하지 않는다.
- `SSE`, `FastAPI`, `diarization pipeline` 같은 구현 용어를 일반 화면에 노출하지 않는다.
- 반복 화면에 긴 사용 설명을 고정 배치하지 않는다.
- 긴 문장을 버튼 안에 넣지 않는다.
- 같은 뜻의 안내문을 섹션 안에서 반복하지 않는다.
- 상태 설명과 동작 설명을 한 문장에 같이 묶지 않는다.

## 색상 사용 규칙

- 화면 컴포넌트에서 `bg-blue-*`, `bg-red-*`, `bg-amber-*`, `text-blue-*`, `border-red-*` 같은 원시 색상 유틸을 직접 조합하지 않는다.
- 상태 안내는 `StatusBanner`와 `ProgressBar`를 우선 사용한다.
- 상태 색상은 `index.css`의 semantic status token을 기준으로 한다: `info`, `warning`, `error`, `success`, `neutral`.
- 버튼, 카드, 메뉴, 빈 상태처럼 반복되는 UI는 색상/테두리/hover를 화면에서 직접 만들지 않고 공통 클래스나 typed component prop으로 지정한다.
- 컴포넌트 호출부에서는 배치, 간격, 반응형 정도만 조합하고 색상 결정은 디자인 시스템에 둔다.
- 참석자 구분처럼 여러 색이 필요한 경우에는 예외적으로 데이터 구분 팔레트를 사용하되, `speaker-*` 계열 공통 클래스 안에서만 정의한다.
