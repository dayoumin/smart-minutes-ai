# Ollama 기반 정리 기능 안정성 검토 계획

## 1. 목표

Ollama 관련 문제를 `설치 오류`라는 하나의 현상으로 다루지 않고, 실행 환경부터 사용자 안내까지 단계별로 구분한다. 사용자는 대화록을 항상 사용할 수 있어야 하며, 정리 기능이 준비되지 않았거나 실패했을 때는 원인과 다음 행동을 한 번에 이해할 수 있어야 한다.

이번 검토의 완료 조건은 다음과 같다.

- 대화록 생성은 Ollama 상태와 무관하게 완료된다.
- 정리 기능의 준비 여부를 실행 파일, 서버, 모델, 추론 단계로 구분할 수 있다.
- 같은 원인이 설정 화면, 기록 정리, 보고서에서 같은 상태와 안내로 표시된다.
- 실패한 정리가 완료로 표시되지 않는다.
- 재시도 가능 여부와 사용자가 해야 할 행동이 명확하다.
- 실제 포터블 환경에서 시스템 Ollama와 앱 관리형 Ollama를 각각 검증할 수 있다.

## 2. 현재 확인된 구조

### 확인된 사실

- `/api/models/status` 한 번의 호출에서 모델 목록 조회, 요약 모델 준비 확인, Ollama 연결 확인이 각각 실행된다.
- 모델 목록 조회 실패는 현재 빈 목록으로 변환되어 `실행 파일 없음`, `서버 중지`, `연결 실패`, `명령 시간초과`를 구분하기 어렵다.
- Ollama HTTP 생성이 연결 계열 오류로 실패하면 CLI 생성으로 다시 시도한다. 두 경로의 제한 시간은 각각 최대 600초다.
- `ensure_ollama_server_running()`의 실패 반환값을 생성 함수가 직접 판정하지 않고 다음 HTTP/CLI 호출로 진행한다.
- 요약 함수는 일부 런타임 오류를 `generation_status.summary=failed`인 정상 형태의 결과로 반환한다.
- 프론트엔드의 전체 요약 완료 안내는 `skipped`만 별도 처리하며, `failed` 결과가 HTTP 200으로 오면 완료 안내가 표시될 여지가 있다.
- 기록 화면은 창 포커스 복귀 때 `/api/models/status`를 다시 호출한다. 상태 조회가 기동 시도와 결합되어 있어 단순 화면 확인도 런타임 동작을 일으킬 수 있다.

### 아직 확인되지 않은 사항

- 사용자가 실제로 본 오류의 정확한 문구, 발생 화면, 발생 시점
- 시스템 설치 Ollama와 앱 관리형 Ollama 중 어느 경로에서 더 자주 발생하는지
- 장시간 회의에서 실제 추론 시간초과가 있었는지
- 포터블 앱 종료 후 관리형 Ollama 프로세스가 정상 정리되는지

위 항목은 추측으로 수정하지 않고 1단계 재현 자료로 확인한다.

## 3. 목표 상태 계약

Ollama 자체 상태와 회의별 생성 상태를 분리한다.

### 실행 환경 상태

| 영역 | 상태 | 의미 |
|---|---|---|
| 실행 파일 | `missing`, `available` | Ollama 실행 파일 탐색 결과 |
| 서버 | `stopped`, `starting`, `ready`, `unreachable`, `failed` | API 연결 및 앱 관리형 프로세스 상태 |
| 모델 | `missing`, `downloading`, `ready`, `invalid` | 선택한 정리 모델의 실제 사용 가능 상태 |
| 정리 기능 | `unavailable`, `ready`, `degraded` | 위 상태를 종합한 사용자 기능 상태 |

### 회의별 생성 상태

`not_started`, `generating`, `completed`, `skipped`, `failed`, `cancelled`를 공통으로 사용한다. `failed`에는 내부 예외 문자열 대신 다음과 같은 안정적인 원인 코드를 붙인다.

- `runtime_missing`
- `server_unreachable`
- `model_missing`
- `request_timeout`
- `invalid_model_response`
- `generation_cancelled`
- `generation_internal_error`

API는 `reason`, `retryable`, `user_action`을 함께 반환한다. 사용자 화면은 이 계약을 번역하고, 백엔드 원문 오류는 로그에만 남긴다.

## 4. 검토 및 구현 순서

### P0. 실제 증상 수집과 재현 기준 고정

- 현재 포터블 앱과 개발 앱에서 오류 문구, 화면, 시간, 선택 모델을 기록한다.
- `/api/health`, `/api/models/status`, 선택 모델 목록, 백엔드 로그를 같은 시점에 묶어 확인한다.
- 시스템 Ollama와 앱 관리형 Ollama를 구분해 기록한다.
- 재현 없이 확인할 수 없는 항목은 배포 전 QA 항목으로 남긴다.

완료 기준: 최소 한 번의 정상 흐름과 의도적으로 만든 실패 흐름이 같은 형식의 증거로 남는다.

### P1. 상태 조회와 실행 명령 분리

- 부작용 없는 `probe`와 서버를 시작할 수 있는 `ensure/start`를 분리한다.
- `/api/models/status`는 상태 조회만 수행하고 Ollama 시작이나 모델 변경을 하지 않는다.
- 모델 목록 조회는 한 요청에서 한 번만 수행하고 짧은 TTL 캐시를 검토한다.
- 빈 목록 반환으로 오류를 숨기지 않고 상태와 원인 코드를 반환한다.
- 시스템 설치본과 앱 관리형 실행 파일의 소유권, 시작 가능 여부, 종료 책임을 명시한다.

완료 기준: 설정/기록 화면을 열거나 포커스해도 Ollama 프로세스가 새로 시작되지 않으며, 동일 상태가 일관되게 반환된다.

### P1. 생성 경로와 오류 계약 통합

- 요약, 주제별 정리, 참석자별 정리, 보고서 생성을 공통 Ollama 게이트웨이로 모은다.
- HTTP 호출과 CLI 대체 실행의 조건을 명확히 한다. 요청이 서버에 도달했을 가능성이 있으면 중복 생성을 피한다.
- 서버 시작, 연결, 추론, JSON 파싱의 제한 시간을 별도로 둔다.
- 생성 함수가 실패 결과를 정상 요약 데이터로 반환하지 않도록 성공 데이터와 실패 응답을 분리한다.
- 실패 시 기존 완료 결과와 대화록을 보존한다.

완료 기준: 모든 생성 API가 같은 오류 형식과 상태 전이를 사용하며, 실패가 HTTP 성공 및 완료 안내로 보이지 않는다.

### P1. 사용자 복구 흐름 정리

- 대화록 탭은 Ollama 오류와 무관하게 정상 사용 가능 상태를 유지한다.
- 기록 정리와 보고서는 실행 전 준비 상태를 확인하되, 상태 확인 실패 자체를 모델 미설치로 단정하지 않는다.
- `준비 필요`, `일시적 연결 실패`, `시간초과`, `응답 형식 오류`를 구분한다.
- 재시도 가능한 오류에는 현재 위치에서 `다시 시도`를 제공한다.
- 설치·모델 준비가 필요한 경우에만 설정 화면으로 이동시킨다.
- 일시적 오류는 토스트, 지속적인 준비 필요·복구 안내는 레이아웃을 흔들지 않는 고정 영역에 표시한다.

완료 기준: 사용자가 오류 문구만 보고 재시도, 설정 이동, 대화록 계속 사용 중 하나를 선택할 수 있다.

### P2. 관측성과 운영 진단

- 로그에 `job_id`, 생성 종류, 런타임 출처, 모델, 단계, 소요 시간, 원인 코드를 구조화해 남긴다.
- 모델 상태 조회 실패와 실제 생성 실패를 별도 이벤트로 기록한다.
- 민감한 회의 본문, 전체 프롬프트, 사용자 경로는 기본 로그에 남기지 않는다.
- 지원 시 한 번에 확인할 수 있는 진단 요약을 검토한다.

완료 기준: 사용자 화면의 원인 코드 하나로 관련 백엔드 로그를 찾을 수 있다.

## 5. 검증 계획

### 자동 테스트

- 실행 파일 없음, 서버 중지, 연결 거부, 모델 없음, 모델 목록 시간초과
- HTTP 생성 성공, 연결 전 실패, 추론 시간초과, 잘못된 JSON, 빈 결과
- 실패 후 기존 요약·주제·보고서가 보존되는지
- `failed` 응답에서 프론트엔드가 완료 안내를 표시하지 않는지
- 창 포커스와 탭 전환이 서버 시작을 유발하지 않는지

백엔드는 Ollama 프로세스와 HTTP를 모의 처리한 단위 테스트를 우선한다. 프론트엔드는 상태 계약별 버튼, 안내, 재시도 동작을 시뮬레이션한다.

### 포터블 수동 검증

| 환경 | 확인할 흐름 |
|---|---|
| Ollama 없음 | 대화록 완료, 정리 준비 안내, 설정 이동 |
| 시스템 Ollama 중지 | 상태 구분, 시작 안내, 대화록 유지 |
| 시스템 Ollama 정상 | 모델 감지, 정리 생성, 앱 종료 영향 없음 |
| 앱 관리형 Ollama·모델 없음 | 런타임 준비 후 모델 받기 |
| 앱 관리형 Ollama 정상 | 앱 시작·종료, 정리 생성, 재시작 후 상태 복구 |
| 네트워크 차단 | 런타임/모델 받기 실패와 기존 대화록 사용 |
| 장시간 입력 | 제한 시간, 중지, 재시도, 기존 결과 보존 |

## 6. 작업 단위와 중단 기준

한 번에 전체를 다시 만들지 않는다.

1. 상태·오류 계약과 테스트를 먼저 추가한다.
2. 백엔드 상태 조회를 계약에 맞춘다.
3. 생성 경로를 공통 게이트웨이로 옮긴다.
4. 프론트엔드 복구 안내를 계약에 연결한다.
5. 포터블 환경에서 수동 검증한다.

각 단계는 관련 단위 테스트, 프론트 타입 검사, `git diff --check`가 통과하면 멈추고 검토한다. P0/P1과 현재 흐름을 막는 P2만 즉시 수정하며, 운영 편의 개선은 핵심 계약이 안정된 뒤 진행한다.

## 7. 이번 검토의 우선 결정

- Ollama는 음성 인식과 대화록 생성의 필수 조건이 아니다.
- 단순 상태 조회는 외부 프로세스를 시작하지 않는다.
- 설정 화면과 생성 화면은 같은 준비 상태 계약을 사용한다.
- 사용자에게는 `요약 프로그램`을 우선 사용하고, 기술 지원 정보에서만 Ollama를 병기한다.
- 실패한 정리보다 기존 정상 결과를 우선 보존한다.
- 실제 오류 문구가 확보되기 전에는 특정 원인을 단정하지 않는다.
