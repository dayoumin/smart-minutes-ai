# 바로록 UI 프로덕션 점검 (2026-10-18)

방향 A「조용한 문서」 재설계(①~④, 2026-10-17 완료) 직후의 전체 UI 점검이다. 화면 단위가 아니라 **화면 × 상태** 단위로 캡처하고, 화면별 검토 세 갈래와 전 화면 공통 검토 한 갈래로 나눠 본 결과를 이 문서 하나에 모은다.

- 범위: HTTPS 웹 앱 UI(Vite 개발 서버 + 가짜 API 응답). 넓은 데스크톱 창과 지원하는 좁은 데스크톱 창. 모바일·PWA는 범위 밖이다.
- 이 점검이 증명하지 않는 것: 실제 로컬 엔진 연결·처리, 모델 받기 복구, 영구 로컬 저장, Tauri 실행 파일, 설치형 Chrome/Edge, 실제 화면 낭독기 음성. 이 부분은 [실제 엔진 점검](#실제-엔진-점검-별도-패스)으로 따로 남긴다.
- 기준 문서: `AGENTS.md`(UI and Copy Work), `docs/design.md`, `docs/ai-assisted-ui-workflow.md` 5절 중지 조건.

## 1. 기준표

"완성도"를 감이 아니라 확인 가능한 항목으로 본다. 발견사항은 아래 ID와 근거 규칙을 함께 적는다.

| R7 | 신뢰와 복구 | 연결 끊김·모델 없음·실패·중지 상태에서 다음 행동이 하나로 분명하다. 편집 중 이탈·삭제 같은 되돌릴 수 없는 동작은 확인한다. 회의록이 이 PC에만 보관된다는 사실이 필요한 곳에 보인다. 음성·대화록이 원격으로 가는 것처럼 읽히는 문구가 없다. | design.md 제품 범위·새 회의록 동작 줄 |
| R8 | 체감 성능 | 긴 대화록(2~3시간, 수천 발화)에서 스크롤·검색·탭 전환이 끊기지 않는다. 오래 걸리는 작업은 진행률·경과 시간을 보여 주고 멈춘 것처럼 보이지 않는다. 최초 진입만 skeleton으로 작업면을 대체한다. | design.md 원칙(skeleton), AGENTS.md Analysis Hang |

심각도:

- **P0** 핵심 흐름이 막히거나 데이터가 사라진다.
- **P1** 핵심 흐름에서 사용자가 헷갈리거나 키보드·보조기술로 쓸 수 없거나, design.md 규칙을 분명히 어긴다.
- **P2** 일부 상태·폭에서 품질이 떨어진다. 현재 흐름·신뢰·저장 데이터에 닿을 때만 바로 고친다(AGENTS.md P2 규칙).
- **P3** 다듬기. 기록만 한다.

### 3.1 회의 상세 (DT)

- **DT-1 [P1·R7] `다시 정리`가 확인 없이 주제별·참석자별 정리를 지운다.** 전체 요약을 다시 만들면 백엔드가 파생 정리를 비우고 보고서를 이전 기준으로 돌린다(`backend/main.py:4210-4226`, 주제별은 `:3690-3693`). 화면은 이 사실을 알면서도(`MeetingHistory.tsx:2442-2447`) 완료 토스트로만 알린다. → 파생 결과가 있으면 실행 전 확인 대화상자.
- **DT-2 [P1·R1] 연결 끊김·파일 저장 실패 때 `Failed to fetch`나 응답 JSON 원문이 배너에 나온다.** 상세의 catch 7곳(`MeetingHistory.tsx:1880, 2304, 2537, 2631, 2719, 2804, 3372`)과 `MeetingDownloadControl.tsx:473-494`가 `error.message`와 응답 본문을 그대로 붙인다. `apiError.ts`의 사용자 문장 변환을 상세는 쓰지 않는다. → `공통` 오류 문장 함수로 일원화(X 묶음과 함께).

### 3.2 새 회의록·분석·웹 연결 (WR)

- **WR-1 [P1·R8] 웹에서 엔진 요청마다 0.5초씩 늦다.** (1단계에서 수정, 5절) `apiBase.ts:143-149`는 주소가 기본값(`http://127.0.0.1:17863`)과 같으면 호출마다 `getTauriApiBase(5)`(100ms × 5)를 다시 돈다. 배포 웹도 `prepare_cloudflare_web.ps1:30`이 같은 주소를 넣어 이 경로를 탄다. 분석 시작 경로는 이 함수를 7번 차례로 불러 최소 3.5초가 걸린다(A1 4.6초, A3 6.1초, S5 1.07초, 45초여야 할 W7이 48.7초인 원인). Tauri는 대기가 없지만 요청마다 `get_backend_base_url`을 부르고 `frontend.log`에 한 줄씩 쌓인다. → Tauri가 아니면 주소를 바로 캐시하고, 재시도 조건을 "Tauri인데 아직 주소를 못 받음"으로 바꾼다. 앱 전체 동작에 효과가 큰 단일 수정이다.

- **WR-3 [P1·R7] 대화록이 저장된 뒤 실패해도 실패 카드는 `다시 시도`만 권한다**(`:2621-2638`). 회의록은 이미 저장되어 있다. → `결과 보기`를 주 버튼으로 두고 "대화록은 저장했습니다"를 먼저 말한다.
- **WR-4 [P1·R5] 분석 시작·중지 패널·실패·완료 때 포커스가 body로 빠진다.** A1~A3 모두 활성 요소가 `body`다. → 진행 카드 제목, `계속`, `중지`, `다시 시도`, `결과 보기`로 각각 옮긴다.
- **WR-5 [P2·R7] 오류 원인과 상관없이 "분석 중 문제가 생겼습니다. 다시 시도해 주세요."와 `다시 시도`만 나온다.** 엔진은 예외 문자열을 그대로 보내고, 단계 시간 초과의 `code`는 프런트가 버린다(`:1786-1788`). → `apiError.ts`에 원인 분류(메모리·파일·저장 공간·연결 끊김·시간 초과)와 원인별 주 동작을 두고, 엔진 SSE 오류에 `code`를 싣는다.

### 3.4 전 화면 공통 (X)

공통 갈래가 따로 지적한 웹 요청 지연(WR-1), 진행 카드 낭독(WR-10), 상세 오류 배너 밀림(DT-8)은 위 항목에 합쳤다. 공통 갈래는 DT-8을 P1로 봤다.

- **X-1 [P1·R5] 포커스 표시가 없거나 대비가 3:1에 못 미친다.** `이번 정리 기준`·`보고 양식` select는 `outline-none`이고 감싸는 label에 `:focus-within`이 없어 표시가 전혀 없다(`index.css:2131-2133`). 설정 토글은 1.24:1(`:575-578`), 대화록 편집칸은 1.53:1(`:2993-2995`)이다. `forced-colors` 대응이 0건이라 Windows 고대비에서는 그림자 링이 사라진다(추정). → `outline: 2px solid transparent` 기반으로 바꾸고, 링은 `--focus-ring-color`(5.02:1) 2px로 통일한다.
- **X-2 [P2·R3·R7] 브라우저 기본 `alert`/`confirm`/`prompt`가 17곳이다**(`Sidebar.tsx` 10곳, `MeetingWriter.tsx` 5곳, `MeetingHistory.tsx:3214`, `Settings.tsx:1041`). 같은 이름 변경·삭제 확인이 상세에서는 인라인 편집·자체 모달이다. 문구에 `폴더 없음`·`HWPX`가 보이고 alert는 `error.message` 원문을 보여 준다. SB-6·SB-8·WR-12가 이 묶음에 속한다. → `components/common/`에 `ConfirmDialog`·`PromptDialog`를 만들고(상세 모달의 포커스 코드 `MeetingHistory.tsx:1735-1793` 일반화), 실패는 지속 표면으로.
- **X-3 [P2·R5] 보이는 버튼 문구가 접근 가능한 이름에 들어 있지 않다**(WCAG 2.5.3). 파일 저장 버튼은 실제로 파일 이름 창을 여는데 바로 저장하는 것처럼 읽힌다. DT-15·SB-10이 이 묶음이다(`MeetingDownloadControl.tsx:505-509, 523`, `MeetingHistory.tsx:461-480`, `Settings.tsx:2005-2008`). → 보이는 문구를 이름으로, 보충은 `aria-describedby`·title로.
- **X-4 [P2·R3] 날짜·시각 형식이 화면마다 6가지이고 `오늘` 기준도 다르다.** 상세 `2026년 10월 18일 일 오후 6:23`, 기록 찾기 `2026년 10월 18일`, 최근 회의록 `오후 6:23`/`10월 17일`, 사이드바 `오늘`/`1일`, 이어서 할 분석 `10. 17. 오후 07:23`, 입력 `2026-10-18 오후 08:23`. 사이드바는 24시간 경과, 최근 회의록은 달력 날짜로 `오늘`을 판정한다. DT-17·SB-9·SB-13의 날짜 부분이 여기에 속한다. → 비어 있는 `src/lib/`에 `dateFormat.ts`(`formatMeetingDateTime`, `formatRelativeAge`, `isToday`)를 두고 카탈로그에 등록한다.
- **X-5 [P2·R3·R4] 같은 동작인데 문구와 버튼 종류가 다르다.** 목록 다시 불러오기가 `다시 시도`(primary)·`다시 확인`(outline)·`다시 불러오기`(ghost)로 갈리고, 같은 설정 > 모델 열기가 새 회의록은 `모델 받기`, 상세는 `모델 준비`다(design.md 72행과 146행이 서로 다른 문구를 지정). `준비 상태 확인`·`상태 확인`·`연결 확인`·`다시 확인`이 섞이고, 보조 버튼 크기가 세 가지다(`Button`에 size prop 없음). WR-15가 이 묶음이다. → design.md 버튼 문구 절에 동작별 문구 표, `Button`에 `size`.
- **X-6 [P2·R3] 같은 상태가 화면마다 다른 이름과 색이다.** 참석자 구분 실패가 사이드바 회색 글자, 상세 경고색 칩, 이어서 할 분석에서는 오류색 칩이다. 진행·중지 이름도 다르고, 백엔드 영어 메시지 번역표가 두 벌이다(`Sidebar.tsx:60-80`, `MeetingWriter.tsx:290-300`). → `lib/statusLabels.ts`에 `{label, tone}`을 모아 함께 쓴다.
- **X-7 [P2·R3·R2] 상세 탭마다 command bar 버튼 크기·행 위치가 다르고, 저장 중 버튼 폭이 바뀐다.** 대화록 탭 14px, 기록 정리·보고서 12px이고 행 y가 414·421·369다. `저장 중`→`저장됨`으로 폭이 줄며 옆 버튼이 움직이고, 같은 순간 제목 줄에도 `저장됨`이 따로 뜬다. DT-6의 버튼 폭 문제와 같은 묶음이다. → 세 탭 같은 크기 클래스·행 높이, 저장 버튼 최소 폭, `저장됨`은 토스트 하나.
- **X-8 [P2·R2·R5] 일시 알림 구현이 네 가지이고, 일부 오류는 5초 뒤 사라지는 토스트다.** `AppToast`, 상세 제목 줄 `save-toast`, 설정의 절대 위치 배너, 사이드바 `alert`. 토스트는 마우스·포커스로 멈추지 않고 `되돌리기` 토스트도 8초 뒤 사라진다. live region이 내용과 함께 새로 마운트되어 낭독되지 않을 수 있다(추정). → `AppToast` 하나, 루트에 항상 있는 live 영역과 큐, 멈춤 지원, 동작 있는 토스트는 자동으로 닫지 않음, 오류는 지속 표면.
- **X-9 [P2·R5] h1이 없고 제목 단계를 건너뛰며, 탐색 랜드마크와 목록 구조가 없다.** 화면 제목은 h2이고 h1은 숨겨진 기록 찾기에만 있다. 사이드바는 `complementary`뿐이고 구역 이름은 span, 행은 div다. 회의를 열어도 `document.title`이 바뀌지 않고 포커스·알림도 없다. → 작업면 제목 h1, 사이드바 `<nav>` + h2 + `ul/li`, 화면 전환 시 h1 포커스와 제목 갱신(사이드바는 작업 중).
- **X-10 [P2·R5] 모션 감소 설정을 거의 따르지 않는다.** `animate-spin` 32곳 중 2곳만 대응하고, `prefers-reduced-motion` 규칙이 0건이다. → index.css에 reduce 블록 하나.
- **X-11 [P3·R3] 디자인 시스템 잔재와 토큰 오용.** 원시 색 유틸·tsx 하드코딩 hex는 0건이다. 대신 쓰지 않는 클래스(`text-h1~text-overline` eyebrow 등), 옛 파랑의 `.dark` 블록, 글자색을 가리키는 `--color-muted`로 만든 진회색 hover, `shadow-sm` 5곳, 11px 글자 11곳, 화면마다 다른 구역 제목 스타일이 남아 있다.

- **X-13 [P3·R3] 비활성 주 버튼·모달 닫기·오버레이 표현이 두 가지씩이다**(회색 vs 청록 50%, 테두리 버튼 vs ghost, 정리 맥락 모달만 blur).

잘 된 점: 원시 색 유틸·하드코딩 hex 0건, `--rail-content` 공유로 본문 열 x 고정, 47장 모두 가로 넘침 0·이름 없는 컨트롤 0, `lang="ko"`와 `<title>`, 글자 색 토큰 모두 4.5:1 이상, `StatusBanner`의 tone별 `alert`/`status` 역할.

## 4. 개선 계획

### 4.1 진행 원칙

- 공통 코드 한 곳을 고쳐 여러 화면이 함께 나아지는 것부터 한다. 그다음은 핵심 흐름(새 회의록 → 분석 → 상세)의 P1이다.
- 묶음마다 `lmo-audio-iterative-dev-loop` 순서를 따른다: 작은 수정 → typecheck → 관련 시뮬레이션 → `capture-ui-audit.mjs`로 해당 ID 재캡처 → 위험에 맞는 agent 검토 → 차단 문제만 수정.
- P2는 AGENTS.md 규칙대로 분류한다. 핵심 흐름, 저장 데이터, 신뢰, 접근성 차단에 닿는 P2는 아래 1~7단계에 넣었다. 나머지는 8단계로 미룬다. P3는 기록만 한다.
- `Sidebar.tsx`, `SidebarRecordMoveMenu.tsx`, `index.css`는 다른 세션이 작업 중이다. 이 파일을 건드리는 항목(사이드바 SB-6~9·13~16, X-1·X-10의 CSS)은 그 작업이 커밋된 뒤 시작한다.

- `settings-backend-restart`: 다운로드 형식은 PATCH 대신 localStorage 즉시 저장을 단언한다. 엔진 저장 검사는 HWPX 자동 저장 스위치로 옮겼다. 불러오기 중 `불러오는 중` 6곳, 닫자마자 저장되는지를 추가했다.
- `settings-model-management`: 상태 응답을 붙잡아 받기 버튼이 없는지 확인한다. 안 받은 모델 option은 비활성이어야 한다(`Locator.isDisabled()`는 `<option>`의 비활성을 읽지 못해 DOM 속성으로 확인). 받은 모델을 고르면 즉시 저장되는지 확인한다.
- `meeting-detail-layout`: 음성 확인 응답을 붙잡아 `확인 중`에서 위치를 재고, 응답을 푼 뒤 `음성 없음`에서 이동 0을 확인한다. 음성 미보관 기록은 확인 중에도 행 0개.
- `new-record-home-flow`, `audio-extract-ui`: 엔진 응답이 없거나 설정을 읽지 못하면 보관 안내 줄에 로컬 처리 문장이 보인다(예전 "줄이 사라짐" 기대를 바꿈).
- `meeting-detail-flow`: 모델이 준비되면 상세의 `모델 준비` 버튼이 정상적으로 사라진다. 사라지는지 확인한 뒤 사이드바에서 설정을 연다(예전에는 요청 지연 덕분에 사라지기 전에 누를 수 있었음).

**검증:** `tsc --noEmit`·변경 파일 ESLint 통과. 같은 Vite 서버(5196)에서 시뮬레이션 8개 통과: `settings-backend-restart`, `settings-model-management`, `meeting-detail-layout`, `new-record-home-flow`, `audio-extract-ui`, `resume-draft-flow`(전체 장면), `analysis-stop-flow`, `meeting-detail-flow`. 독립 agent 검토는 P0·P1 없음이었고, P2 3건(부분 결과 기록의 음성 행, 재시작 중 설정 변경, 음성 행 테스트가 이동을 고정하지 못함)은 반영했다. 실행 중 다른 세션의 파일 수정으로 Vite가 페이지를 새로 고쳐 생긴 일시적 실패 1건은 다시 돌려 통과했다. 가짜 API 기준이며 실제 엔진·배포 웹·데스크톱 앱은 확인하지 않았다.

**미룬 것 (독립 검토 P3, 2026-10-18):**

- 모델 탭 두 카드가 같은 로딩 문장을 쓴다.
- 닫을 때 저장과 진행 중 저장이 같은 값으로 PATCH를 한 번 더 보낼 수 있다.
- `불러오는 중` 글자 폭이 컨트롤 폭과 달라 좁은 창에서 설명 줄바꿈이 바뀔 수 있다.
- 설정된 모델이 설치되지 않은 경우를 고정하는 시뮬레이션이 없다.
- 기존 문제: 일반 설정 저장이 실패하면 600ms마다 다시 시도하며 오류 배너가 깜박인다.
- 음성 확인 뒤 참석자 구분 안내 줄이 생기며 생기는 이동은 DT-11로 남긴다.
